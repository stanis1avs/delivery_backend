# Стенд оценки распределения заказов

Отвечает на вопрос, на который тесты ответить не могут: **насколько хорошо** система назначает курьеров. Тест говорит «назначилось или нет», стенд — какой ценой.

```bash
npm run simulate                                              # базовый сценарий
npm run simulate -- --couriers 30 --orders-per-hour 12 --hours 2 --repeat 5
npm run simulate -- --strategy current --seed 7
```

## Что настоящее, а что смоделировано

Подбор курьера выполняет **настоящий `findBestCourier`** против настоящих PostGIS и OSRM. Рейтинг пересчитывает **настоящий `modules/reliability.js`**. Это принципиально: если переписать логику подбора внутри стенда, метрики будут описывать копию, а не систему — и дефекты вроде неверного имени таблицы (BUG-101) в такой копии не проявятся.

Смоделировано только то, что на качество подбора не влияет: доставка уведомления, реакция курьера, его перемещение. Redis и Telegram не участвуют — их механика закрыта тестами (`tests/worker.test.js`, `tests/telegram.test.js`).

Прогон идёт в отдельной базе `delivery_sim`, которая пересоздаётся каждый раз. Рабочая и тестовая базы не затрагиваются.

## Параметры

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--couriers` | 20 | размер флота |
| `--orders-per-hour` | 60 | интенсивность потока (пуассоновский) |
| `--hours` | 2 | длительность виртуального времени |
| `--radius` | 0.03 | разброс точек в градусах (≈3 км) |
| `--tick` | 5 | шаг времени, как у воркера |
| `--invite-ttl` | 300 | сколько ждём ответа курьера |
| `--repeat` | 3 | прогонов на стратегию, результаты усредняются |
| `--seed` | 42 | база для ГПСЧ; прогоны воспроизводимы |
| `--strategy` | все | прогнать одну стратегию |

Курьеры делятся на три профиля поведения — `reliable`, `picky`, `flaky` — с разной вероятностью принять, отклонить или проигнорировать приглашение.

## Метрики

| Метрика | Зачем |
|---|---|
| ETA до забора, медиана и p95 | Основной показатель качества подбора |
| Ожидание курьера | От появления заказа до принятия |
| Не назначено | Заказы, которым курьера не нашлось |
| Приглашений на назначение | 1.0 — идеал; выше — курьеров дёргают зря |
| Доли отказов и игноров | Косвенный признак неудачных назначений |
| Джини по нагрузке | 0 — поровну, 1 — всё одному. Против выгорания топов |
| **Кандидатов, медиана** | Сколько курьеров рассматривала формула |
| **Был выбор, % подборов** | Доля подборов, где кандидатов больше одного |

Последние две — самые важные для интерпретации. Если выбора почти не бывает, любая формула стоимости даст один и тот же результат, и настраивать её бессмысленно.

## Что уже показали прогоны

**При загруженном флоте формула не работает.** Сценарий 14 курьеров / 45 заказов в час: медиана кандидатов **0**, выбор был в **0.4%** подборов. Стратегии `current`, `nearest` и `rating-heavy` дали посимвольно одинаковые метрики — выбирать было не из кого. Узкое место здесь размер флота, а не коэффициент в скоринге.

**При свободном флоте различия появляются, но малы.** Сценарий 30 курьеров / 12 заказов в час, усреднение по 5 seed'ам: выбор в 100% подборов, медиана кандидатов 5. Разброс ETA между стратегиями — единицы секунд, в пределах шума. Заметно отличается только `fair`: задействует ощутимо больше курьеров, то есть ровнее размазывает нагрузку.

**Практический вывод.** Коэффициент `RATING_BONUS_SECONDS = 30` менять смысла нет: при текущем разбросе рейтингов (σ≈0.7) он даёт поправку около 20 секунд против сотен секунд разницы в маршрутах. Рейтинг начнёт влиять либо при большем весе, либо когда рейтинги разойдутся сильнее.

## Ограничения

- Метрики сравнивают стратегии **между собой**, а не предсказывают абсолютные значения в проде.
- Курьер моделируется упрощённо: он «телепортируется» по маршруту за время, которое вернул OSRM, без учёта пробок и промежуточных остановок.
- Свободные курьеры стоят на месте; перераспределяются они только за счёт того, что заканчивают заказ в точке доставки.
- Для сравнения с околооптимальным назначением нужен внешний солвер (VROOM, OR-Tools) — здесь его нет.
